---
title: Get payout status
api: GET /api/rfq/status/{quoteId}
description: Current status of a payout, by quote ID. Fields are progressively populated as the payout moves through its lifecycle.
---

Lookup is by `quoteId` — the value returned from [`POST /rfq/execute`](/api-reference/payouts/execute) (or any successful row of [`POST /rfq/execute-batch`](/api-reference/payouts/execute-batch)). Response is wrapped in `{ "success": true, "data": <QuoteStatus> }`.

Fields on `data` are populated progressively. Pre-settle reads typically show just `quoteId`, `status`, `quotedToAmount`, plus the deposit instructions for S2F flows. Post-settle reads add `actualToAmount`, `deltaAmount`, `settleTxHash`, and the resolved `transactionId`.

Scope: `payouts:read`.

## Headers

<ParamField header="Authorization" type="string" required>
  `Bearer sk_test_…` (sandbox) or `Bearer sk_live_…` (production).
</ParamField>

## Path parameters

<ParamField path="quoteId" type="string" required>
  UUID of the locked quote, as returned from `/rfq/execute`.
</ParamField>

## Response

<ResponseField name="quoteId" type="string">
  Echoed back.
</ResponseField>

<ResponseField name="status" type="string">
  Coarse-grained payout status. See [Core Concepts](/concepts#transaction-status) for the lifecycle. Common values include `awaiting_escrow_deposit` (S2F, pre-deposit), `processing`, `delivered`, `failed`.
</ResponseField>

<ResponseField name="transactionId" type="string">
  UUID of the underlying payout. Use with [`GET /payouts/{id}`](/api-reference/payouts/get) for the full transaction read (fees, amounts, metadata, etc.). Populated once the payout has been written to the transactions table.
</ResponseField>

<ResponseField name="quotedToAmount" type="number">
  Destination amount as quoted at lock time, in the destination currency.
</ResponseField>

<ResponseField name="actualToAmount" type="number">
  Destination amount that actually settled. Populated after delivery.
</ResponseField>

<ResponseField name="deltaAmount" type="number">
  Signed difference between `actualToAmount` and `quotedToAmount` — useful for surfacing FX slippage post-fact.
</ResponseField>

<ResponseField name="settleTxHash" type="string">
  On-chain settlement transaction hash (S2F and fiat-to-stablecoin flows).
</ResponseField>

<ResponseField name="onrampProvider" type="string">
  Opaque routing identifier of the onramp leg.
</ResponseField>

<ResponseField name="offrampProvider" type="string">
  Opaque routing identifier of the offramp leg.
</ResponseField>

<ResponseField name="paymentUrl" type="string">
  For onramp flows that required a hosted payment page.
</ResponseField>

<ResponseField name="bankingInstructions" type="object">
  Map of `string` → `string`. For F2F / onramp flows that settle by bank transfer. Keys vary by rail.
</ResponseField>

<ResponseField name="errorMessage" type="string">
  Set when `status` is `failed`. Surfaces the root cause for partner-side debugging.
</ResponseField>

### Stablecoin-to-fiat fields

<ResponseField name="escrowAddress" type="string">
  On-chain address your wallet sent (or must send) the source stablecoin to.
</ResponseField>

<ResponseField name="depositAmountAtomic" type="string">
  Atomic-units integer string. Parse with `BigInt`. Example: `"300000"` = 0.3 USDC at 6 decimals.
</ResponseField>

<ResponseField name="tokenAddress" type="string">
  ERC-20 contract address of the source stablecoin.
</ResponseField>

<ResponseField name="chainId" type="integer">
  EVM chain id of the source token.
</ResponseField>

<ResponseField name="escrowChainId" type="integer">
  Chain on which this quote's escrow slot lives.
</ResponseField>

<ResponseField name="escrowState" type="string">
  Escrow lifecycle state for S2F flows. Typical progression: `awaiting_deposit` → `confirmed` → `released`.
</ResponseField>

<ResponseField name="actualUsdcReceived" type="number">
  Final USDC amount the escrow received before settle. Populated after deposit confirmation.
</ResponseField>

## When to poll vs subscribe

Polling is fine for low-volume integrations and for ad-hoc status checks. For production traffic, subscribe to `payout.status.updated` and `payout.delivered` via [Webhooks](/guides/webhooks) — same data, push-based, no polling cost.
