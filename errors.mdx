title: Errors & retries
description: HTTP status codes, error shape, idempotency, and retry guidance for the Teel API
---

Teel returns standard HTTP status codes. The body is JSON with a stable, machine-readable `code` you can switch on, plus a human-readable `error` message.

```json
{
  "code": "MAX_ACTIVE_SUBSCRIPTIONS_EXCEEDED",
  "error": "subscription limit reached (max 25 per account)"
}
```

**Switch on `code`, not `error`.** Each `code` has exactly one meaning and never changes once shipped — it's part of the contract. The `error` message is for humans and may be reworded at any time. Some errors also include a `details` object with structured context (e.g. the offending field and the bound it violated).

## Status codes

| Code | When |
| --- | --- |
| `200 OK` | Successful read |
| `201 Created` | Successful create |
| `202 Accepted` | Asynchronous work enqueued (e.g. a payout batch, or a webhook delivery replay) |
| `400 Bad Request` | Your request was malformed — bad JSON, missing required field, validation failure (invalid URL, unknown event type, etc.) |
| `401 Unauthorized` | Auth missing or invalid — see [Authentication](/authentication) |
| `403 Forbidden` | Authenticated, but the key lacks the required scope or your business is not allowed this action |
| `404 Not Found` | Resource doesn't exist, or exists but isn't yours. Both answer the same body, so a `404` never reveals another business's resource. |
| `409 Conflict` | Request conflicts with current state — e.g. you've reached a per-account limit (25 subscriptions, etc.) |
| `422 Unprocessable Entity` | Validation passed but business rule rejected — e.g. payout amount below the provider's minimum |
| `429 Too Many Requests` | Rate limit hit — back off per `Retry-After` |
| `5xx Server Error` | Our side. Safe to retry per the schedule below. |

## Error codes

The codes a partner key can receive, with the status each is sent with. New codes may be added; a shipped code never changes meaning, so treat an unknown code by its status. Some payout refusals also carry `"success": false` next to `code` and `error`.

### Authentication and access

| Status | Code | Meaning |
| --- | --- | --- |
| `401` | `UNAUTHORIZED` | Key missing, malformed, expired or revoked. |
| `403` | `INSUFFICIENT_SCOPE` | The key lacks the scope the route needs. |
| `403` | `FORBIDDEN` | Not allowed for another reason, such as a currency outside your business's product scope or an entity you are not a member of. |
| `403` | `ENV_SCOPE_MISMATCH` | A key for one environment was used against the other environment's host. |
| `403` | `PAYOUTS_NOT_ENABLED` | Payouts are not enabled for your business. |
| `403` | `APPROVAL_REQUIRED` | Your business approves payouts before they execute, so a single-call execute is refused. |
| `403` | `COLLECTIONS_NOT_ENABLED` | Your business does not hold the collections product this request needs. |
| `403` | `COLLECTIONS_FROZEN` | Collections is switched off for your business; its records are read-only. |
| `403` | `MANUAL_CONVERT_DISABLED` | Settling to fiat is paused for your business. |
| `429` | `RATE_LIMITED` | Rate limit hit. Wait for `Retry-After`. |

### Request shape

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | The request is structurally wrong. |
| `400` | `INVALID_JSON` | The body is not valid JSON, or a required field is missing. |
| `400` | `INVALID_PARAMETER` | A parameter has the wrong shape or value, such as a malformed UUID. |
| `400` | `MISSING_PARAMETER` | A required parameter is absent. |
| `400` | `ENTITY_REQUIRED` | The key's owner belongs to more than one business; name one in `X-Teel-Entity-Id`. |
| `400` | `VALIDATION_FAILED` | Field values break the schema. `details.violations` lists `{path, code, message}` per field. |
| `400` | `FIELD_NOT_WRITABLE` | The request sets a field, or query parameter, the partner API does not accept. |
| `400` | `IDEMPOTENCY_KEY_INVALID` | `Idempotency-Key` is not 8–255 characters from `[A-Za-z0-9_-]`. |
| `400` | `INVALID_PAYOUT_RAIL` | `payoutRail` is not a rail Teel knows. |
| `400` | `OUTGOING_INVOICE_DOCUMENT_REQUIRED` | A settlement needs `outgoingInvoiceDocumentFileId`. |
| `400` | `AMOUNT_IS_INVALID` | `amountIs` is neither `delivery` nor `spend`. |
| `400` | `SPEND_MODE_UNSUPPORTED` | `amountIs=spend` on a settlement whose rail cannot debit exactly the spend. |
| `413` | `REQUEST_BODY_TOO_LARGE` | The body is over the size limit. |

### Not found

A resource that is not yours answers the same `404` as one that does not exist.

| Status | Code | Meaning |
| --- | --- | --- |
| `404` | `NOT_FOUND` | The resource does not exist or is not yours. |
| `404` | `RECIPIENT_NOT_FOUND` | The recipient does not exist or is not yours. |
| `404` | `BUSINESS_NOT_FOUND` | The business does not exist or is not yours. `PUT /recipients/{id}` sends it as `400`. |
| `404` | `PAYMENT_METHOD_NOT_FOUND` | The payment method does not exist or is not yours. |
| `404` | `WEBHOOK_SUBSCRIPTION_NOT_FOUND` | The webhook subscription does not exist or is not yours. |
| `404` | `WEBHOOK_DELIVERY_NOT_FOUND` | The webhook delivery does not exist or is not yours. |

### Conflicts

| Status | Code | Meaning |
| --- | --- | --- |
| `409` | `IDEMPOTENCY_KEY_REUSED` | The `Idempotency-Key` was used with a different request. |
| `409` | `IDEMPOTENCY_REQUEST_IN_FLIGHT` | The first request with this key is still running. Back off per `Retry-After`. |
| `409` | `CONFLICT` | The request conflicts with the resource's current state. |
| `409` | `ALREADY_EXISTS` | The resource already exists. |
| `409` | `REFERENCED_BY_OTHERS` | The resource cannot be deleted while something else points at it. `DELETE /recipients/{id}` sends it as `400`. |
| `409` | `MAX_ACTIVE_SUBSCRIPTIONS_EXCEEDED` | You have reached the active webhook subscription limit. |
| `409` | `PAYMENT_LINK_NOT_VOIDABLE` | The payment link has left `open`, so it cannot be voided. |
| `409` | `insufficient_available_balance` | The settlement is more than the uncommitted balance, or another settlement of it is in flight. Lower case for historical reasons. |
| `409` | `SETTLEMENT_REQUIRES_DASHBOARD_AUTHORIZATION` | The settlement wallet can only be moved from the dashboard. |
| `409` | `OWNER_MFA_REQUIRED` | A wallet the request needs waits on an owner setting up their authenticator. |
| `409` | `MFA_REQUIRED` | A wallet the request needs waits on you setting up your authenticator. |
| `409` | `WALLET_DISABLED` | A wallet the request needs is switched off. |

`POST /rfq/execute` can also answer `409` with the code nested inside `error`, for example `{"success": false, "error": {"code": "rate_moved", …}}`:

- `rate_moved`: the price moved past your tolerance since the quote. Nothing was locked; get a new quote.
- `route_infeasible`: the route you pinned can no longer carry this payout. Nothing was locked; get a new quote and pick its route.

### Server side

| Status | Code | Meaning |
| --- | --- | --- |
| `500` | `INTERNAL_ERROR` | Something we did not expect went wrong. |
| `502` / `503` | `DOWNSTREAM_UNAVAILABLE` | A service the request depends on could not be reached. Retry. |
| `503` | `QUOTE_UNAVAILABLE` | A price or fee needed for the request is not available right now. Retry. |
| `503` | `ADDRESS_SCREENING_UNAVAILABLE` | The crypto address could not be screened. Retry. |
| `503` | `OFFRAMP_DISABLED` | The settlement path you asked for is switched off. |

## What is and isn't retryable

| Status | Retryable? | Why |
| --- | --- | --- |
| `4xx` (except `429` and `409 IDEMPOTENCY_REQUEST_IN_FLIGHT`) | **No** | The request will fail the same way until you change it. Retrying wastes your rate budget. |
| `429` | **Yes**, after `Retry-After` | The server told you when to come back. Respect it. |
| `409 IDEMPOTENCY_REQUEST_IN_FLIGHT` | **Yes**, after `Retry-After`, with the same `Idempotency-Key` | The first request with this key is still running. The retry replays its result once it finishes. |
| `5xx` | **Yes**, with exponential backoff | Likely transient — our side. |
| Network timeout / connection error | **Yes**, with exponential backoff + idempotency | The server may or may not have processed your request — see [Idempotency](#idempotency). |

### Recommended retry schedule

For `5xx` and network errors:

```
attempt 1 → wait 1s
attempt 2 → wait 2s
attempt 3 → wait 4s
attempt 4 → wait 8s
attempt 5 → wait 16s
attempt 6 → give up, surface to the user
```

With ±20% jitter to spread retry storms across many clients. Total wait: ~31 seconds across 5 attempts.

For `429` and `409 IDEMPOTENCY_REQUEST_IN_FLIGHT` responses, ignore the schedule above and wait the number of seconds in the `Retry-After` header. A retry before that just adds load.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 13

{"code": "RATE_LIMITED", "error": "rate limit exceeded"}
```

## Idempotency

Mutating POSTs accept an **`Idempotency-Key`** header — `POST /rfq/execute`, `POST /rfq/execute-batch`, `POST /rfq/confirm-escrow-deposit`, `POST /recipients`, `POST /recipients/bulk`, `POST /recipients/{id}/retry`, `POST /recipients/{id}/payment-methods`, and `POST /webhooks/subscriptions`. Include a UUID you generate; if the same key is sent within 24 hours, Teel returns the original response without creating a duplicate.

```bash
curl https://api.teel.finance/rfq/execute \
  -H "Authorization: Bearer sk_live_…" \
  -H "Idempotency-Key: 7f3c2a91-4e5b-4d8c-9a1f-3e2b1c4d5e6f" \
  -H "Content-Type: application/json" \
  -d '{"fromCurrency": "USD", "toCurrency": "PHP", "amount": 1000, "recipientId": "...", "routeProtocol": "..."}'
```

**Always set this on payout execution.** A network timeout on a POST without `Idempotency-Key` leaves you uncertain whether the payout was created — and retrying might double-charge your customer. With the header set, retry is safe. Reusing a key with a *different* body returns `409 IDEMPOTENCY_KEY_REUSED`.

The header is **not** required on quotes (those are idempotent by request shape) or on reads, and is not honored on update / delete endpoints.

Collections follow the same rules on `POST /collections/payment-links` and `POST /collections/buyers`. **Settlements are different:** `POST /collections/receiving-accounts/offramp` *requires* `Idempotency-Key` (missing is `400 MISSING_PARAMETER`), and the key is stored on the settlement itself rather than in the 24-hour cache. A retry with the same key returns that settlement for as long as it exists, and the same key with a different request returns `409 IDEMPOTENCY_KEY_REUSED`. See [Create settlement](/api-reference/collections/settlements/create).

## Rate limiting

Per-key default: **60 requests per minute, burst 20**. A route in one of the families below is limited by its family instead of the default, and the `X-RateLimit-*` headers describe that family's limit. Webhook replay is the one exception: it keeps the default and adds its own per-account limit.

| Endpoint | Limit | Notes |
| --- | --- | --- |
| `GET /quotes/*` | 120/min, burst 40 | Quotes are cheap; higher limit reflects their typical poll-during-checkout pattern |
| `POST /rfq/execute`, `POST /rfq/execute-batch`, `POST /rfq/confirm-escrow-deposit`, `POST /payouts/document` (`payouts_write`) | 30/min, burst 10 | Creating money movements should be relatively rare |
| `POST /webhooks/subscriptions/{id}/rotate-secret` (`rotate_secret`) | **3/min, burst 3** | Manual ops affordance |
| `POST /webhooks/deliveries/{id}/replay` | **5/min, burst 5** per account, on top of the default | Manual ops affordance, not a programmatic endpoint |
| `GET /collections/*` (`collections_read`) | 120/min, burst 40 | Reads and settlement previews |
| `POST`/`PUT`/`DELETE` payment links and buyers (`collections_write`) | 30/min, burst 10 | Creating a link locks a rate; creating a buyer can mint an address |
| `POST /collections/receiving-accounts/offramp` and `/offramp/document` (`settlements_write`) | 10/min, burst 5 | Settlements move money |

Every response carries:

```http
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 47
X-RateLimit-Reset: 1700001234
```

`X-RateLimit-Reset` is a Unix timestamp (seconds) when the bucket fully refills.

If you find yourself consistently near the limit, batch where possible (`POST /rfq/execute-batch` instead of N calls to `POST /rfq/execute`) and cache quote results client-side for ~30s rather than re-quoting on every page render.

## What we never do

- **We do not return 4xx for transient issues.** If you got a `400` / `401` / `403` / `404` / `409`, the request is wrong; do not retry. The exceptions are `429` and `409 IDEMPOTENCY_REQUEST_IN_FLIGHT`, which say when to come back in `Retry-After`.
- **We do not silently truncate fields.** If a field exceeds a limit, you get a `400` with the field name and the violated bound. Quietly truncating user-supplied amounts is a class of bug we deliberately avoid.
- **We do not return generic 500s if we can avoid it.** Validation failures are `400` / `422`; permission failures are `403`; missing resources are `404`. A `500` from our side really means "something we didn't expect went wrong" — please report it to **support@teel.finance** so we can fix it.

## Examples

### Idempotent payout with retries

```javascript
import { randomUUID } from "crypto";

async function createPayoutWithRetries(payload) {
  const idemKey = randomUUID();
  let delay = 1000;
  for (let attempt = 1; attempt <= 5; attempt++) {
    const res = await fetch("https://api.teel.finance/rfq/execute", {
      method: "POST",
      headers: {
        "Authorization": `Bearer ${process.env.TEEL_API_KEY}`,
        "Idempotency-Key": idemKey,
        "Content-Type": "application/json",
      },
      body: JSON.stringify(payload),
    });

    // 2xx — done.
    if (res.ok) return res.json();

    const err = res.status >= 400 && res.status < 500 ? await res.json() : null;
    const inFlight = res.status === 409 && err?.code === "IDEMPOTENCY_REQUEST_IN_FLIGHT";

    // 4xx (except 429 and an in-flight 409) — bug in our request; do not retry.
    if (err && res.status !== 429 && !inFlight) {
      throw new Error(`Teel ${res.status}: ${err.error}`);
    }

    // 429 or in-flight 409 — server-told wait.
    if (res.status === 429 || inFlight) {
      const retryAfter = Number(res.headers.get("Retry-After") ?? 1);
      await new Promise((r) => setTimeout(r, retryAfter * 1000));
      continue;
    }

    // 5xx or network error — exponential backoff with jitter.
    const jitter = 0.8 + Math.random() * 0.4;
    await new Promise((r) => setTimeout(r, delay * jitter));
    delay *= 2;
  }
  throw new Error("Teel API: 5 retries exhausted");
}
```

Same `Idempotency-Key` across all retries — Teel returns the originally-created payout on retry rather than creating duplicates.
